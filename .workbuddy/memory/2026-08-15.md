## 启动即铺满工作区 (commit 37c3739)
- 坑：`resizable(False,False)` 会钳制 geometry → 启动没铺满（上一轮引入）。修正：窗口保持可缩放（铺满前提），三路保证「最大化不可用」：① 去 WS_MAXIMIZEBOX（最大化钮置灰）② `_maximize_to_workarea` 里 `maxsize(工作区)+minsize(640,400)` 钳制拖边角不超工作区 ③ 双击标题栏因最大化钮去掉而失效。

## 最大化彻底不可用 (commit bc04c51)
- **关键诊断结论**：`WS_MAXIMIZEBOX` 样式位本来就**没设**——Tk 原生标题栏默认 GWL_STYLE=0x56000000（WS_TILEDWINDOW+WS_SYSMENU+WS_MINIMIZEBOX），`0x10000` 位是 0。所以前两轮「去掉 WS_MAXIMIZEBOX」是白改，可点的最大化钮是 Tk 标题栏模型自己画的，不受该样式位控制。
- **必赢打法**：子类化 WndProc 系统层拦截 → `_install_no_maximize_wndproc()`：吞 `WM_SYSCOMMAND(wparam&0xFFF0==SC_MAXIMIZE 0xF030)` + `WM_NCLBUTTONDBLCLK(HTCAPTION)`。最大化钮/双击标题栏/任务栏右键最大化/Aero 吸附全失效。`self._orig_wndproc` 存原过程、`self._wnd_proc_holder` 保活回调防 GC；在 `_setup_frameless` 铺满+去样式位之后调用；`__init__` 初始化两引用。
- 教训：Tk Windows 标题栏按钮**不能靠窗口样式位控制**，要拦消息。

## 启动真铺满工作区 (commit a9429ca)
- 坑：`SetWindowPos` 设 2560×1368 后，Tk 用「内容请求尺寸」在重新布局时把窗口缩回 640×426（诊断 `actual rect=(201,235) 640x426` 抓到）。
- 修：`_maximize_to_workarea` 改为先 `root.minsize(w,h)+root.maxsize(w,h)`（都=工作区，Tk 内部尺寸目标即工作区）再 `SetWindowPos` → 不再缩回（诊断 `actual rect=(11,61) 2560x1368` 确认）。

## 启动真最大化（最终） (commit 42ae59d)
- **最终结论**：SetWindowPos(缩回640x426)/ShowWindow SW_MAXIMIZE(缩回960x620) 都被 Tk 用「内容请求尺寸」覆盖，且 state 仍是 normal。**唯一对的做法是 Tk 原生 `root.state('zoomed')`**——进入 zoomed 状态后 Tk 自维护窗口尺寸（=工作区），不再被内容尺寸覆盖。原 overrideredirect 时代 zoomed 失效，native 标题栏下无此问题。
- 实测：`state('zoomed')->state=zoomed`，`actual rect=(0,34) 2560x1334`（工作区 2560x1368，底部对齐屏幕底，不被遮）。
- WndProc 同步增拦 `SC_RESTORE`（0xF120），窗口锁定最大化：还原钮/系统菜单/任务栏右键最大化都无效。
- 教训：**Tk 最大化必须用 `state('zoomed')`，不要用 SetWindowPos/ShowWindow 手动模拟**（会被 Tk 布局覆盖）。

## 任务栏图标（最终） (commit d10e77d)
- **根因**：之前只设 `WM_SETICON ICON_SMALL(16)`，而 Windows 任务栏按钮请求 `WM_GETICON` 优先取 `ICON_BIG(32)`，取不到就回退进程可执行文件图标（pythonw 的 python 默认图标）——所以一直显示 python。
- **修**：`_set_win_icon` 同时设 ICON_SMALL+ICON_BIG 并保活两个 HICON；叠 `root.iconbitmap()` Tk 双保险；`SetCurrentProcessExplicitAppUserModelID("FileSearcher.App")` 独立分组；窗口显示后 400ms/1200ms 延迟重设两次（防任务栏快照时机/缩放丢失）。`_set_win_icon(img=None)` 复用 `self._ico_path` 支持延迟重设。
- 诊断确认 `small=True big=True`。若用户仍见 python 图标 = Windows 任务栏图标缓存，需清缓存（改 AUMID 或重启 explorer）。

## 首次启动任务栏图标（commit dc58fdc）
- **根因**：`SetCurrentProcessExplicitAppUserModelID` 在 `WM_SETICON` **之前**调用 → Windows 首次设置 AUMID 时用「当时的窗口图标」（默认/通用）给任务栏分组做快照，所以**首次启动显示通用图标**；恢复窗口时任务栏按钮重建、重读窗口图标才正确。
- **修**：调换顺序——先 `WM_SETICON`(small+big) 设窗口图标 → 再 `iconbitmap` → 最后 `SetCurrentProcessExplicitAppUserModelID`。AUMID 值从 `FileSearcher.App` 换成 `FileSearcher.App.2`，强制丢弃旧缓存分组。
- 教训：**AUMID 必须在窗口图标设置之后设置**，否则快照到默认图标。

## 视频播放器「双击慢/空窗不播放」排查（跨项目，未改代码）
- 症状：从 FS 双击视频 ①很久才有反应 ②窗口起来不播放。资源管理器双击正常。
- 结论 1（慢）：FS 无辜（`_shell_open` 后台线程 ShellExecuteExW 毫秒级返回，debug.log 零 open-error）。慢在播放器冷启动——`%APPDATA%\com.hjf.videoplayer\shutdown.log` 显示 `app starting`→`setup: showing` 固定 0.6~10s。资源管理器快是因为播放器已在跑、走单实例转发。
- 结论 2（空窗不播放，核心 bug）：播放器单实例回调 `lib.rs` 里 `put(path)` 后 `let _ = app.emit("open-file-available")` 吞了 Result——若主实例 WebView2 没起来/前端没跑到 `listen`（App.vue 393 行），事件永久丢失，文件躺在 pending_open mailbox 没人取。onMounted 的 take 兜底（App.vue 397）只在挂载时跑一次，单实例热路径救不了。修法=前端加窗口 focus 时主动 `take_pending_open_file` 兜底（三路互补：onMounted / listen / focus）。

## ★ 双击视频打开问题·最终真相（2026-08-15 晚，已解决）
- **上文结论 1/2 全是错的弯路**（被假象误导）。真根因：**FS 进程是我用 `Start-Process -WindowStyle Hidden` 从 WorkBuddy 工具链拉起的，跑在隔离沙箱会话（非用户 Session 1 桌面会话）**。该会话里 `os.startfile`/`ShellExecute`/`explorer.exe` 拉起另一个 GUI 程序（Tauri 播放器）时被 Windows 静默拦截——进程起不来或卡死。
- **关键对比**：文档中心（用户从桌面正常启动，Session 1）双击同一文件秒开秒播；FS（工具拉起，隔离会话）双击要么无反应要么空窗。我用工具链 `python -c os.startfile(文件)` 复现：返回 OK 但播放器根本没启动（shutdown.log 无新增）——实锤是会话隔离，非代码写法。
- **走过的弯路（勿再犯）**：先后怀疑并改了 ①ShellExecuteExW 加 NOASYNC/DDEWAIT ②删标志位 ③os.startfile 后台守护线程→主线程 ④怀疑播放器单实例 emit 丢失。全是徒劳，因为根因在进程会话不在代码。
- **解法**：PyInstaller 打包 `dist\FileSearcher.exe` → 复制到 `C:\Users\hjf\Desktop\FileSearcher.exe` → **用户自己双击桌面 exe 启动**（Session 1）。用户实测：双击视频秒开秒播，且任务栏图标问题也顺带解决（正常会话里 WM_SETICON/AUMID 才生效）。
- **代码定稿**：`open_with_default` = 主线程 `os.startfile(os.path.normpath(path))`，无线程无标志位。
- **今后流程（用户明确要求）**：改完代码 → PyInstaller 打包 → 覆盖桌面 exe → 让用户自己启动。绝不再从工具拉起 FS 进程。
